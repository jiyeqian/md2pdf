# 开发与发布

## 本地开发

```bash
git clone https://github.com/jiyeqian/md2pdf.git
cd md2pdf
npm install
npm start
```

运行项目校验：

```bash
npm test
npm run check:consistency
```

WebApp 与跨运行环境的人工验收要求见[交接与一致性说明](cross-runtime-handoff.md)和[验收记录](web-app-acceptance.md)。

## 分支与合并

以 `main` 为集成基线，在功能分支中开发并推送到 CNB；所有改动通过 CNB 合并请求进入 `main`。合并前检查改动、流水线和验收结果，并由项目负责人确认。合并后同步本地 `main` 并核对提交。发布版本另行确认。

分支用于隔离改动，工作区用于隔离本地工作。按任务选择：

- 继续同一项尚未完成、需要一起验收的任务：使用原分支和工作区。
- 开始独立任务：从最新 `main` 创建任务分支。对应长期工作区干净且空闲时可复用；如需与未完成任务并行，则创建独立工作区。需要分别验收或独立合并的改动使用不同分支。
- 仅查看、讨论或审阅时，通常无需创建分支。切换工作区前，检查未提交、被忽略和未同步的内容；不得覆盖或丢弃尚未处理的工作。
- 长期工作区可用于后续任务，目录名不必与当前任务分支名相同。有独立提交尚未合入的分支应保留，先审阅处理，再为其他任务选择工作区。

任务合并并核对同步后，检查未提交、被忽略及未同步内容；确认安全后清理临时工作区和对应本地、CNB 远端任务分支。长期工作区保留；存在无法确认归属或去向的内容时暂停清理。

合并前按以下步骤核对：

1. 查看合并请求的改动范围、验收记录和风险；重要改动由项目负责人独立审阅。
2. 确认 `cnb/pull_request` 的“校验”流水线已出现并通过。检查缺失、运行中、失败或取消时，不合并；排查原因并重新检查。
3. 核对通过的流水线所检查的来源提交和目标 `main` 提交仍是当前版本。如果任一分支更新，针对更新后的两端重新触发检查并等待通过；必要时更新来源分支以触发新的合并请求流水线。
4. 获得项目负责人确认后，在 CNB 手动合并。合并后同步本地 `main`，核对合并提交及 CNB 到 GitHub 的同步结果。

CNB 的状态检查规则仅在存在检查时要求通过；目标分支更新后，旧检查也可能仍显示通过。以上核对依赖人工执行，核对与合并之间仍有竞态，不得把旧状态或缺失状态视为通过。不要使用强制合并绕过检查。

## 版本与发布

`package.json` 是唯一版本来源，CLI 与服务端、静态 WebApp 共用该版本。发布 tag 使用 `v版本号` 格式；三种发布产物应来自同一提交。项目的 CNB 流水线负责构建和 npm 发布，凭据配置及运行维护说明不属于终端用户使用指南。
