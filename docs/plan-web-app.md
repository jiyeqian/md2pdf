# md2pdf 在线应用评估与实现路径

> 目标：把 md2pdf 从 CLI 扩展为在线应用——输入 Markdown，实时预览 HTML 排版，并可下载 PDF。
> 参考形态：https://md-to.com/zh-cn/markdown-to-pdf/
> 目标地址：https://md2pdf.app.workbuddy.host/
> 本计划已获授权更新；实现与部署仍需分别获得授权。

## 一、接手评估与结论

**可以接手推进，本地可用版本的技术可行性较高；指定平台上线仍需验证。** 推荐复用现有排版能力，新增 Node HTTP 服务与极简编辑器，保持 CLI 行为和零 npm 运行时依赖的安装体验。

2026-10-02 对核心代码、包配置和校验脚本进行了只读评估，未运行测试或验证部署平台。当前没有发现阻碍本地开发的硬性问题，但本计划不能作为部署成功或零回归的保证。

| 项目 | 判断 | 证据与边界 |
| --- | --- | --- |
| 在线 Markdown → HTML → PDF | 可行，有现有资产可复用 | 需要先拆分渲染、文件处理与打印职责 |
| 内核已经解耦 | 尚未完成 | 实际入口是 `renderOne(mdPath, opts, chrome, marked, hljs, tmpRoot)`，不是独立的 `render(mdText, opts)` |
| 指定平台可运行 Chromium | 待验证 | npm 安装能力不能证明浏览器可启动 |
| 分页预览与 PDF 完全一致 | 待实测 | 非 GB 类型使用两种分页机制 |
| 对 CLI 零影响 | 兼容目标 | 通过回归检查降低风险，不能保证无回归 |
| 公网上线 | 有前置条件 | 必须补齐安全边界、浏览器恢复机制及目标环境证据 |

## 二、现有资产与实际结构

### 2.1 可复用资产

- `src/md2pdf.mjs`：Markdown 解析、文档预设、章节编号、图表题注、参考文献、HTML 生成及 Chrome/CDP 打印。
- `src/profiles.mjs`、`src/numbering.mjs`：五类文档预设和编号方案。
- `assets/`：页面模板、主题 CSS、GB 标志。
- `vendor/`：marked、MathJax、Mermaid、highlight.js、Paged.js，支持现有 CLI 零 npm 运行时依赖。
- `templates/`、`examples/`：五类文档的模板与示例。
- `ci/validate.sh`、`ci/checks.mjs`：结构、语法、源码一致性和 HTML 行为校验；`ci/inspect-pdf.mjs` 用于检查 PDF 书签与内链。

### 2.2 尚需拆分的职责

`renderOne()` 当前读取 Markdown 文件，根据文件名和 frontmatter 检测类型，解析相对图片路径，生成 HTML，写临时 HTML，并调用 Chrome 打印。HTML-only 分支可以跳过 Chrome，但函数整体尚不是接受文本的独立渲染 API。模块末尾还会直接调用 `main()`，不能直接 import 作为服务内核。

抽取时应保留文件名、资源基路径、选项默认值及文档类型检测上下文，避免文本 API 改变 CLI 的既有行为。

### 2.3 两条 HTML 与 PDF 路径

| 产物 | 当前机制 | 在线应用用途 |
| --- | --- | --- |
| 调试 HTML | 未分页的完整 HTML | 正文样式预览 |
| 分页 HTML | 所有类型使用 Paged.js | 分页预览候选方案 |
| PDF | GB 使用 Paged.js；非 GB 使用 Chrome 原生分页 | 正式导出 |

**分页预览不能直接承诺与 PDF 完全一致。** 需要验证长表格、代码块、公式、Mermaid、页眉页脚与分页结果；浏览器和服务端字体差异也会影响布局。非 GB 的现有 PDF 路径保持不变。

MathJax、Mermaid、Paged.js 和 GB 标志目前使用本机文件 URL，相对图片也会转为文件 URL。在线场景需要明确的资源 URL 或内联策略。

## 三、推荐架构与产品边界

采用同一部署单元：静态前端 → Node HTTP 服务 → HTML 渲染内核 / Chrome PDF 打印。

- `GET /`：编辑器页面及必要的静态资源。
- `POST /api/render`：输入 Markdown 与受限选项，返回 HTML 和文档类型。
- `POST /api/pdf`：输入 Markdown 与受限选项，返回 PDF 二进制。
- 前端左侧编辑、右侧 iframe 预览；输入防抖，取消旧请求或忽略过期响应。
- PDF 任务使用有容量上限的串行队列；浏览器可复用，每个任务的页面与资源状态需隔离。

首版保留主题、类型、目录、字号、边距及编号控制，默认加载 `examples/general.md`。文件上传、多主题扩展和富文本复制作为后续可选工作。

首版预览按上述 `/api/render` 路线上传内容到服务端，下载 PDF 也上传内容。若改为浏览器本地渲染，需要另行评估前端模块适配，不能同时宣称当前架构仅下载时上传。

服务端 Chrome 路线适合复用现有导出能力；浏览器打印可作为另行评估的降级选项，但其书签、内链和分页结果需实测，不能笼统断言全部丢失。

## 四、安全、隐私与服务生命周期

将可信本地文件的 CLI 扩展为公网服务，需要新增以下边界，同时保留 CLI 的现有本地功能：

- API 参数白名单与类型、范围校验，不开放服务器文件路径、输出路径或浏览器启动参数。
- 请求体、文档复杂度、队列容量与任务执行时间上限；队列满时返回明确错误。
- 对输入中的原始 HTML、脚本、事件属性及危险 URL 制定清理策略；预览 iframe 隔离应用权限，同时允许受控的 MathJax、Mermaid、Paged.js 执行。
- PDF 浏览器限制文件与网络资源访问，阻止用户内容读取服务器文件或访问内网、回环及云元数据地址；远程图片需明确允许策略，不能只依赖启动时的禁用后台联网参数。
- 明确相对图片的支持范围：仅提交 Markdown 文本不能复用用户本机相对文件；附件上传不纳入首版，除非另行授权。
- 明确告知内容上传及保留策略，日志不记录正文。当前打印路径会写临时 HTML，不能宣称“内存即弃、完全不落盘”。实施时选择内存渲染或临时落盘并在成功、失败、超时及服务退出时清理。
- Chrome 启动失败、CDP 断连、页面加载失败与排版等待超时应显式失败；补齐浏览器重启、未完成任务处理及服务关闭机制。现有等待逻辑和进程管理不能直接视为长期服务实现。
- `--no-sandbox` 是现有启动参数，不是安全措施；部署时需根据运行环境选择浏览器沙箱与外围隔离方案。

## 六、部署与依赖决策

系统 Chrome 可通过 `MD2PDF_CHROME` 或探测机制使用；Puppeteer/Playwright 管理的浏览器可作为候选方案。**能安装 npm 包且能出网，并不能证明浏览器可运行。** 系统库、架构、进程权限、沙箱、字体、下载限制及磁盘/内存配额都需核实。

目前没有本次评估取得的目标平台工具或运行证据，不能把 `workbuddy.host`、目标域名或自带 Chromium 标为“确定可行”。具体工具名称与参数以部署时可用接口为准。

若需要浏览器管理依赖，优先放在独立的服务端 package 中，确保 CLI 安装不会下载 Chromium。根包 `optionalDependencies` 仍可能被默认安装，`devDependencies` 在生产安装中可能被省略，均不能直接当作依赖隔离保证。

按实际部署结构决定是否增加根包 `start`、是否将 `web/` 纳入 npm `files`；检查 CLI tarball 自包含性及安装行为，不为部署自动改变 npm 发布范围。

## 七、推进顺序与兼容要求

1. 先完成内核拆分和现有校验适配，确认 CLI 回归检查通过。
2. 完成受限 HTTP 服务与最小前端，验证本地完整链路。
3. 完成真实 Chrome 的 PDF 与失败恢复验证，记录预览差异。
4. 明确授权部署后，验证目标环境并上线。

每个阶段保持最小完整改动。现有 CLI、文档预设、主题、参考文献、编号及 npm 安装体验作为兼容要求；测试通过是必要证据，不是零风险保证。当前阶段只更新计划，不实施、安装依赖、发布 npm 包或部署。
